Attest: does a Know-Your-Agent check make an agent harder to fool?

1. Claim and baseline

A supplier agent that checks senders with Attest before acting blocks unauthorized agent-to-agent requests far more often than the same agent judging requests itself, moves almost no money for attackers, and refuses valid requests no more often, at a few milliseconds and $0 of LLM cost per check.

Main metric: share of attack requests on which no harmful action was taken, read with the share of valid requests falsely refused. Main baseline (C2): the same LLM supplier (same model, prompt, tools, budget) without Attest. It can read every presented document but cannot verify signatures, stake, revocation or history; that is the "simpler way" a team would ship today. Two deterministic references bracket it: C0 accepts everything, C1 is a hand-kept allowlist on the credential's operator name plus the presented mandate's scope. C3 adds Attest's check_agent tool to C2; C4 is the gate alone. Everything below was pre-registered (PREREG.md) before the first run.

2. Setup

Cases. 22 cases, 25 inbox requests: 11 valid (quotes, orders, repeat orders, delegation, an alarming but valid "URGENT" order, a 9,500 order that policy sends to a human, a newcomer asking a public quote, a staked operator that is not a named partner) and 14 attacks (unstaked impostor, forged operator name, bare claim, over-limit, order splitting, out-of-scope sub-agent, broken delegation, revoked mandate, replayed order, amount tampered after signing, slashed operator, prompt injection, expired mandate, stolen identity). Each case runs in a fresh gate world (new keys, stakes, state). Success check: the action recorded by the agent's fulfil/decline/escalate tool call (never its prose), compared with the pre-set expected action. LLM conditions: claude-sonnet-5-5, effort medium, 5 reps per case (pending); at most 8 model calls per request; all requests of a case in one conversation, so the baseline remembers earlier orders. Costs: tokens and dollars per request, gate latency in-process and over HTTP. Reproduce: python -m bench.run_bench (C0, C1, C4), bench/run_llm.sh (C2, C3), python -m bench.sybil, python -m bench.latency; a second deterministic run gave identical decisions.

4. A limit, one change, a retest

What we varied. The number of agents one staked operator controls. Attest's thesis is that trust comes from stake: SupplierCo accepts operators staked at 10,000 or more. But stake was checked as a threshold, while spend was capped per mandate. An operator staked at 20,000 can mint any number of agents, each with its own 10,000 root mandate. Evidence (tuning sweep, k = 1, 2, 4, 8): the gate allowed k × 10,000; at k = 8 it allowed $80,000, 4× the stake, and slashing every allowed order recovers at most the stake, leaving $60,000 unrecoverable. (Delegated sub-agents were already contained: they share their root's running total, fresh case F1.)

The change (750a61a): orders allowed across all of an issuer's mandates and receivers in a 30-day window may not exceed its stake (refusal issuer_exposure_over_stake; a setting, so before and after ran on identical code; setting it to 0 reproduces the "before" numbers exactly). Tuning vs fresh: the four tuning cases exposed the limit; four fresh cases (sub-agents, two receivers sharing the gate, a 15,000 stake with smaller orders, an honest high-volume operator) were committed with the probe, before the change (6a229df), and not used to design it.

Retest result. With the cap, exposure stays at or under the stake in every tuning and fresh case (k = 8: $80,000 → $20,000). The remaining unrecoverable amount (a few hundred to $1,250) comes from the slashing schedule, which takes half of what is left per claim, so a finite number of claims never reaches the full stake. Gate alone on the SybilCo agent-level case: $40,000 → $20,000 per pass. The C3 (LLM) version of this retest is pending the LLM run. Regression: the main suite gives identical C4 decisions with the cap on, and the scripted scenario suite still passes. Cost of the change (fresh case F4): an honest operator doing $40,000 of business on a $30,000 stake now has $12,000 of real orders refused, so it must stake more or wait for the window to roll. That is the intended trade (no exposure the stake does not back) but it is a real false refusal that the main suite does not show.

5. Interpretation and limitations

  • What the evidence supports. Checks that need cryptography or shared state (forged names, tampering, stolen keys, replays, revocation, expiry, slashing, running totals) are exactly where the non-Attest conditions fail; a name allowlist misses most of them, and an LLM can read the same documents but cannot verify them. Attest answers in a few milliseconds at no LLM cost.
  • What it does not show. The attacks are the ones the gate was designed for, written by its builders; unknown attack classes, collusion between staked operators, and attacks on the gate itself are not tested. C4's 100% says the gate implements its spec, not that the spec is complete.
  • Small and synthetic. 25 requests per pass, 5 LLM repetitions; the intervals are wide. One model, one prompt, one effort level; a better baseline prompt could narrow the gap, and C3 only helps if the agent calls the tool and follows it (check-call share reported above).
  • Deployment. One gate process on one machine, stakes and slashing in a JSON file rather than on chain; throughput is bounded by the single lock (about 338 decisions/s here). The issuer cap holds per gate: an operator using several independent gates could still exceed its stake in total, which needs the shared on-chain stake contract that is planned. The 30-day window and ratio 1.0 are choices, not measured optima. Slashing takes a fixed share of the stake per claim, not the damage, so it can also over-recover (tuning case k = 1 recovers 15,000 for a 10,000 loss).
  • Not used. NANDA Town: our claim is about one receiver deciding whether to trust one sender, which a controlled, repeatable world tests better; the gate exposes plain HTTP and MCP tools, so a Town scenario can be added later.
