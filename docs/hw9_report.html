Summary. A fresh agent that had never seen Attest signed itself up from AGENTS.md alone and placed a $600 order with a shop agent. The shop, equally fresh, registered at the gate, checked both orders in its inbox, fulfilled the legitimate one at the correct price ($585) and declined an unstaked order we planted. The buyer then read the reply and verified the gate's signed receipt. All six checks, fixed in the repository before each run, passed: in the first run and again on the final, merged documentation.

We then tested a crash of the shop between checking and replying. The failure we predicted did not happen: the restarted shops (Opus 5.5 and Haiku 5.5) worked around it by searching the gate's public log of every decision. That observation motivated one change, repeat checks: the same request checked again now returns its original answer. After the change, the restarted shops re-checked instead of reading the public log, in fewer steps. 8 new regression tests guard the change, and 7 of them fail on the old gate.

1. Usable interface and instructions 2 pts

What Attest offers. Before an agent acts on a request from another agent, it asks the Attest gate:

  • Who deployed the sender: a credential signed by an operator (a company or person).
  • Does that operator have enough stake behind it for this receiver?
  • May the sender do this: a mandate of actions and a maximum amount, delegable only by narrowing.
  • Is it all still valid: expiry, revocation, signatures, freshness, running spend.

The gate answers allow, refuse, escalate or unknown, with a reason and a receipt signed by the gate.

How the documentation was checked before any agent saw it. We followed it step by step on a fresh sandbox gate and in a clean virtualenv. That found two bugs a newcomer would have hit, both fixed before the cold-start runs (commit 3850b2d):

  1. The documented install could not start the gate. pip install left out the network/ package and the static/town pages, so the gate crashed at import. The packaging is fixed, and we checked it with a clean install.
  2. Sub-agents were always refused. attest agent delegate made sub-agents whose mandate outlived its parent, so the gate refused every one of them (attenuation_violation). The child's expiry is now capped at its parent's, with a regression test.

2. Cold-start integration and meaningful result use 4 pts

2.1 Set-up: what the client agents got, and what they did not

Attest is shared infrastructure, so the test has two interacting agents: a buyer and a shop. Each was a fresh, headless Claude Code session (claude -p, default model Opus 5.5) that had never seen the repository.

Each session got only:

  • AGENTS.md;
  • the URL of a fresh sandbox gate;
  • a shared drop-box folder (its only channel to the other agent);
  • a task in plain words.

It did not get: a call sequence, the expected answer, our code, the web (WebFetch and WebSearch were off), MCP servers, or skills.

The Attest package was preinstalled as a regular, non-editable install. Each session worked in its own folder outside the repository. The harness only takes turns. It never relays, edits or interprets a message: the agents write and read the drop-box themselves.

2.6 Independent or self-run, and manual help

  • Self-run. We wrote the harness and the task prompts. The clients were fresh Claude Code sessions (Opus 5.5; Haiku 5.5 in two crash runs) with no memory of our project, started by our harness on our machine.
  • No manual help during any run. No human message reached an agent. The harness only started each phase, planted the probe and, in crash runs, moved the shop's replies aside. Resumed phases continue the same session; the prompts are in usability/tasks/.
  • Isolation is instructed and audited, not enforced. The sessions could technically read other files. usability/check_isolation.py scans every tool call and found no access to the repository, the gate's files or the other agent's folder.
  • Changes made after a run, all in git history:
    • the isolation checker's URL fix (after real-1);
    • check R1 and the crash scenario, added after real-1 but before any crash run (1576ca9);
    • the two confirmation runs, registered before they ran (ab40abb).
    No check was changed after a run that it scores.

3. Boundary, improvement, and rerun with regression tests 2 pts

3.1 The boundary tested: a shop that crashes between checking and replying

The gate refuses a request whose one-time nonce it has already seen (replay). This protects against replays, but it means a receiver that crashes after asking cannot ask again. Agents retry tool calls, crash and receive messages twice, so this is a realistic failure. We added a crash phase (--crash-retry):

  1. After the shop has checked and replied, the harness moves its replies and saved receipts aside. The keys stay.
  2. A fresh shop session handles the same inbox, told only that it was restarted after a crash and lost its work.

Check R1 (registered in 1576ca9 before any crash run) passes when, at the end, the buyer's order has a fulfilled reply carrying a genuine allow receipt, and the probe is declined. Prediction: R1 fails, because a re-check gets replay and the shop declines a good order.

3.2 What we observed before the change

The predicted failure did not happen, for either model. Both restarted shops had read in AGENTS.md that a request can be checked once. So instead of re-checking, they searched the gate's public log of every decision (GET /receipts) for their old receipts, verified the signatures and replied correctly.

This is an honest negative result for the prediction, and a real finding about the interface: the only way to recover was a workaround through a log of everyone's decisions, which AGENTS.md itself lists as a privacy limit. A client that simply re-checks would get replay.

3.3 The improvement: repeat checks (commit df78644)

  • When the same, unchanged request is checked again at the same receiver within 20 minutes, the gate returns its original decision and receipt, marked "repeat": true. Unchanged means the same id (the hash of the body), a valid signature, and the same credential and chain.
  • Nothing is counted twice and no new receipt is written.
  • A different or altered request reusing the nonce is still refused as replay.
  • AGENTS.md gained a section, Checking the same request again: act on a request at most once; if your records show you acted, don't act again; if you have none (you crashed), act now.
  • The SDK and MCP tool expose repeat, and the NANDA Town seller treats a repeat as a duplicate.

Regression tests (tests/test_repeat.py, 8 tests; 7 fail on the old gate, all pass now). They cover:

  • a repeat returns the identical receipt;
  • spend is counted once (this one passed before too, since the old gate simply refused);
  • refusals are repeated;
  • nonce reuse with new content is still replay;
  • a copy with a broken signature or a swapped mandate chain is not answered from the earlier check;
  • other receivers get nothing;
  • the proof-of-work flow is unchanged;
  • a third party checking a copy first no longer locks the receiver out.

Also passing: all 57 repository tests, the scripted gate scenarios (15a: repeat; 15b: nonce reuse is still replay) and the 22 NANDA Town integration tests. The HW7 deterministic benchmark is unchanged: Attest alone blocks 100% of attacks with 0% false refusals.

3.5 What improved, what did not, what remains unproven

  • Improved. Recovery after a crash is now one supported call. All three post-change runs re-checked and got the original answer, with 0 reads of the public log, versus 2 per run before. The restarted shop needed fewer steps: Opus 4 → 3 tool calls, Haiku 7 → 4 tool calls and 8 → 5 turns. The NANDA Town seller with its journal off now applies a double-delivered order once (it used to get replay). A third party can no longer use up a receiver's check.
  • Did not improve. Correctness did not change. Every shop acted correctly before the change too, thanks to the workaround. The Haiku shops' "fail" on R1 is their own escalation policy, not an error, and the change cannot affect it.
  • Unproven. We ran one run per condition and model, all self-run. A non-Claude agent, an agent built by another team, and finding the documentation without being handed it are all untested. The gate still cannot tell whether a receiver already acted on a request; keeping that record stays the receiver's job, and AGENTS.md says so. A long hand-off (over 10 minutes) would still expire the request.
