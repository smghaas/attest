Summary. A buyer agent that had never seen Attest signed itself up from AGENTS.md alone and ordered from an equally fresh shop agent. The shop registered at the gate, checked every order, fulfilled the legitimate one at the right price and declined an unstaked one we planted. The buyer verified the gate's signed receipt. 1. Usable interface and instructions 2 pts

Before an agent acts on another agent's request, it sends the request to the Attest gate. The gate checks:

  • who deployed the sender (a credential signed by an operator);
  • whether the operator has enough stake behind it;
  • what the sender may do (a mandate of actions and a maximum amount, delegable only by narrowing);
  • whether it is all still valid.

It answers allow, refuse, escalate or unknown, with a reason and a receipt signed by the gate. AGENTS.md covers each rubric item:

Capability, accessWhat is checked, the three roles, the four decisions. HTTP (with an OpenAPI schema), CLI, Python SDK and MCP server. Running a gate takes two commands, and sandbox sign-up is free test stake.
InputsThe envelope (credential, mandate chain, signed request), with full JSON. The receiver's check signature on a sandbox. Canonical JSON and Ed25519 signing rules, so any language can take part.
OutputsEvery response field with full JSON, how to verify the receipt, what to do with each decision, all 32 reason codes, and repeat.
Permissions, limitsSandbox stake is not money, everything is public, requests expire after 10 minutes, rate limits, who may revoke, claim or dispute, one gate process, and HTTP errors (400, 401, 403, 404, 409, 413, 429, 503).
export ATTEST_URL=http://127.0.0.1:8402                   # the documented example, real output
attest operator create AcmeCorp                           # key pair + 10,000 free test stake
attest receiver create acme-supplies --min-stake 5000 --escalate place_order=2000
attest agent create acme-buyer --operator AcmeCorp --actions request_quote,place_order --max 3000
attest request acme-buyer acme-supplies place_order 1200 --check   # ALLOW ok ... place_order 1,200 within limit 3,000
attest request acme-buyer acme-supplies place_order 2500 --check   # REFUSE cumulative_over_limit (order splitting)

Checked before any agent saw it. We followed the documentation step by step on a fresh gate and in a clean virtualenv, and fixed two bugs a newcomer would have hit (commit 3850b2d):

  1. A pip install left two packages out, so the gate could not start. Fixed and checked with a clean install.
  2. Sub-agents made with attest agent delegate outlived their parent, so the gate always refused them. Fixed, with a regression test.

2. Cold-start integration and meaningful result use 4 pts

2.1 Set-up

Attest is shared infrastructure, so two agents interact through it: a buyer and a shop. Each is a fresh headless Claude Code session (claude -p, Opus 5.5) that has never seen the repository.

  • Each got only: AGENTS.md, the URL of a fresh sandbox gate, a shared drop-box folder (its only channel to the other agent), and a task in plain words.
  • None got: a call sequence, the expected answer, our code, the web, MCP servers or skills.
  • The harness only starts each phase. It never relays or edits messages.
PhaseTask (abridged; verbatim in usability/tasks/)
shop setup"You run the online shop widget-shop … register the shop at the gate … You choose the minimum stake and the policy."
buyer"Buy 30 units of part X-200, for about $600 in total, from widget-shop, which only deals with agents it can vet through Attest. Put your order as ONE JSON file in to-widget-shop/."
harnessPlants one probe: an order of $487.50 from an operator with no stake, which should not be served.
shop inbox"Process every file … vet the sender with Attest … decide fulfilled, declined or escalated … reply … keep the gate's receipt." Price: X-200 at $19.50.
buyer confirm"Find out whether your order went through … check that the receipt is genuine, if you can." Write outcome.json.

2.2 Success criterion, fixed before the run (usability/CHECKS.md, commit 20655be)

The run succeeds when all six checks pass. usability/score.py computes them from artifacts only: gate receipts, gate state, drop-box files and transcripts, never the agents' own claims.

B1The buyer got sandbox stake, made an agent whose mandate covers the order, and sent a $500–700 order signed by its key and addressed to widget-shop.
S1The shop registered widget-shop with a key it holds.
S2The gate has a receipt for every order in the inbox.
S3Every reply follows the gate's decision, and the buyer's order was allowed and fulfilled at $585 (30 × $19.50).
S4The planted unstaked order was declined.
B2The buyer's outcome.json matches the real reply. Bonus: it checked the receipt signature correctly.

2.5 Self-run, manual help

  • Self-run. We wrote the harness and prompts. The clients were fresh Claude Code sessions (Opus 5.5, plus Haiku 5.5 in two crash runs).
  • No manual help. No human message reached an agent during any run.
  • Isolation is audited, not enforced. usability/check_isolation.py scans every tool call.
  • Pre-registration. Checks were committed before the runs they score: R1 in 1576ca9, the confirmation runs in ab40abb. The only post-run change was the isolation checker's URL fix; the original verdict is kept.

3. Boundary, improvement, and rerun with regression tests 2 pts

Boundary tested. The gate refuses a request whose one-time nonce it has already seen (replay), so a receiver that crashes after checking cannot ask again. A new phase (--crash-retry) tests this:

  1. The harness moves the shop's replies and receipts aside, as if it had crashed and lost its work.
  2. A fresh shop session handles the same inbox.

Check R1 (registered before any crash run) passes when the buyer's order ends up fulfilled with a genuine allow receipt and the probe is declined. Our prediction: R1 fails, because a re-check gets replay.

Observed. The prediction failed for both models. The restarted shops had read in AGENTS.md that a request is checked once. Instead of re-checking, they searched the gate's public log of every decision for their old receipts and verified them. Recovery worked, but only through a log that AGENTS.md itself flags as a privacy limit. A client that simply re-checked would get replay.

Improvement: repeat checks (commit df78644).

  • The same unchanged request, checked again at the same receiver within 20 minutes, returns its original decision and receipt with "repeat": true. Unchanged means the same id, a valid signature, and the same credential and chain.
  • Nothing is counted twice, and no new receipt is written.
  • An altered request, or a new one reusing the nonce, is still replay.
  • AGENTS.md now says to act on a request at most once, the SDK and MCP tool expose repeat, and the NANDA Town seller treats a repeat as a duplicate.

Regression tests. tests/test_repeat.py has 8 tests, and 7 fail on the old gate. They check:

  • the receipt is identical and nothing is counted twice;
  • refusals are repeated;
  • nonce reuse is still replay;
  • tampered copies and swapped mandate chains are not answered from the earlier check;
  • other receivers get nothing;
  • proof of work is unchanged;
  • a third party checking first cannot lock the receiver out.

Also passing: all 57 repo tests, the gate scenarios and the 22 NANDA Town tests. The HW7 benchmark is unchanged (Attest alone blocks 100% of attacks, with 0% false refusals).

  • Improved. Crash recovery is now one supported call: 0 public-log reads in every post-change run, against 2 before. It took fewer steps: Opus went from 4 to 3 tool calls; Haiku from 7 to 4 tool calls and 8 to 5 turns. A NANDA Town seller with its journal off now applies a double-delivered order once; before, it got replay.
  • Did not improve. Correctness: every shop acted correctly before the change too, thanks to the workaround. Haiku's R1 "fail" comes from its own escalation policy, which the change cannot affect.
  • Unproven. We ran one run per condition, all self-run. Non-Claude clients, another team's agent and discovering the docs unaided are untested. Whether a receiver already acted remains its own record to keep, and the docs say so.

4. How to repeat the test

git clone https://github.com/smghaas/attest && cd attest && python3.11 -m venv .venv && . .venv/bin/activate && pip install -e . pytest
python usability/run_coldstart.py --run-id my-run                  # §2; needs the `claude` CLI; starts its own sandbox gate
python usability/run_coldstart.py --run-id my-crash --crash-retry  # §3  (MODEL=claude-haiku-5-5 for the Haiku runs)
python usability/score.py usability/runs/my-run                    # re-score from artifacts
python -m pytest -q tests && python run_scenarios.py --spawn       # regression tests and gate scenarios
